## 3. Verbatim import of the three source roots

Create the parent Workspace folder first — defensive, since `import-dir` has been observed to create its own destination tree on its own, but that behavior isn't documented API contract, only an empirical observation from one run; `mkdirs` is idempotent (no error if the folder already exists), so there's no cost to being explicit:
```
databricks workspace mkdirs /Workspace/Users/<userName>/databricks-integration -p <profile>
```

Same `import-dir --overwrite` pattern `/deploy-databricks-dashboard` section 4.3 already uses for `chec_local_interpreter` — repeat it here for that package AND add `chec_impacto` and `scripts` (which that command does not upload):

```
databricks workspace import-dir src/chec_local_interpreter /Workspace/Users/<userName>/databricks-integration/chec_local_interpreter_src/chec_local_interpreter --overwrite -p <profile>
databricks workspace import-dir src/chec_impacto /Workspace/Users/<userName>/databricks-integration/chec_impacto_src/chec_impacto --overwrite -p <profile>
databricks workspace import-dir scripts /Workspace/Users/<userName>/databricks-integration/scripts_src/scripts --overwrite -p <profile>
```

**`scripts/` is a third source root and it is not optional.** `src/chec_local_interpreter/ventanas_015.py` does `from scripts.extract_geometrias_014 import ...` at **module import time** (line 43), so `05` and `06` do not merely fail late at the geometry step — they fail on the import itself with `ModuleNotFoundError: No module named 'scripts'`. `scripts/` is a real package (it has `__init__.py`), which is why it uploads and imports like the other two. Its `sys.path` entry is part of the canonical shim block in step 4.

If `import-dir` rejects a non-notebook file in any of the three, fall back to individual `databricks workspace import <target_path> --file <local_file> --language PYTHON --format RAW --overwrite -p <profile>` calls for the rejected files, same fallback `/deploy-databricks-dashboard` documents.

`import-dir` has no exclude/filter mechanism — if any of the three local package trees has `__pycache__/*.pyc` from local runs, they get uploaded too (confirmed empirically: a run against a real workspace uploaded 106 stale `.pyc` files across the two `src/` packages this way; `scripts/` has its own `__pycache__` too). Clean them up right after the imports — do not leave them in the Workspace:
```
databricks workspace delete --recursive /Workspace/Users/<userName>/databricks-integration/chec_local_interpreter_src/chec_local_interpreter/__pycache__ -p <profile>
databricks workspace delete --recursive /Workspace/Users/<userName>/databricks-integration/chec_impacto_src/chec_impacto/__pycache__ -p <profile>
databricks workspace delete --recursive /Workspace/Users/<userName>/databricks-integration/scripts_src/scripts/__pycache__ -p <profile>
```
Both `src/` packages have `__pycache__` nested under multiple subpackages, not just at the root — find every one locally first (`find src/chec_local_interpreter src/chec_impacto scripts -type d -name __pycache__`) and repeat the delete for each match; deleting only the top-level `__pycache__` leaves the nested ones behind.

Also upload `requirements.txt` next to the two package roots, so the notebooks in step 4 can `%pip install -r` it from the Volume-relative bootstrap — but upload a **trimmed copy**, not the repo file verbatim. Verified by statically diffing every third-party top-level import across `src/chec_impacto` and `src/chec_local_interpreter` against `requirements.txt`: the local-dev/test-only entries `jupyter`, `ipykernel`, `pytest`, `python-dotenv`, `pydantic` are never imported by either package or by any of the 6 active notebooks (Databricks already provides its own notebook kernel, so `jupyter`/`ipykernel` would be actively redundant there; `pytest` only runs the test suite, never imported at runtime; `python-dotenv`/`pydantic` have zero references anywhere in this repo). Everything else in `requirements.txt` IS reachable from `src/` (confirmed via AST import-graph audit, 2026-07-24) — do not trim further than this without re-running that audit, since guessing which packages a given notebook "probably" doesn't need is exactly the kind of assumption that caused the `optuna` `ModuleNotFoundError` in the first place.
```
grep -vE '^(jupyter|ipykernel|pytest|python-dotenv|pydantic)$' requirements.txt > /tmp/requirements-databricks.txt
databricks workspace import /Workspace/Users/<userName>/databricks-integration/requirements.txt --file /tmp/requirements-databricks.txt --language PYTHON --format RAW --overwrite -p <profile>
rm -f /tmp/requirements-databricks.txt
```

## 4. Notebook bootstrap shim (staged copies only — never touch the originals)

**Hard invariant**: every notebook uploaded in this step is a modified COPY prepared in a scratch location (e.g. `/private/tmp/.../scratchpad/`), never the file under `notebooks/project_flow/` in this repo. Only the notebook's bootstrap cell(s) — the code that computes where the repo/data/`src` live — is rewritten in the copy. All other cells (markdown, analysis, outputs) stay byte-identical to the repo original. After this step finishes, `git status --porcelain notebooks/project_flow/` in this repo MUST show zero changes — if it does not, something wrote to the wrong path; stop and fix that before continuing.

**Strip cell outputs from every staged copy before upload.** `databricks workspace import --format JUPYTER` enforces a 10MB payload limit, and for this set that is not an edge case — it is the norm. Measured on the current files:

| Notebook | With outputs | Stripped |
|---|---|---|
| `01_uiti_vano_clima` | **81.43 MB** | 0.05 MB |
| `02_uiti_vano_kmeans` | **9.39 MB** | 0.08 MB |
| `03_uiti_vano_trayectorias_circuitos` | **11.58 MB** | 0.09 MB |
| `04_uiti_vano_trayectorias_vano` | **12.31 MB** | 0.09 MB |
| `05_mil_vano_ventana` | 0.07 MB | 0.06 MB |
| `06_uiti_vano_explicabilidad_simulador` | 0.06 MB | 0.05 MB |

Three of the six are over the ceiling outright and `01` is 8× it — those four embed a full interactive Plotly panel as `text/html` in their last cell. Clear `outputs` and `execution_count` on every code cell of every staged copy; this discards stale rendering from a prior local run, never source code, and it regenerates on the first real run in Databricks. Do it for all 6 as a standard step, not only the ones currently over the limit.

The 6 notebooks fall into 3 bootstrap variants.

**General rule (applies to all 3 variants)**: the shim replaces ONLY the root-resolution logic — the `find_repo_root()` / `resolve_project_root()` function + its call (Variants A and B), or the `Path.cwd()` walk-up loop (Variant C) — plus the `sys.path`-insertion block that immediately follows it, where there is one. **Every other line already present in that same bootstrap cell is left completely unchanged**, and so is every later cell that references the root variable or any name derived from it. This works because the replacement always **aliases the exact same root-variable name the notebook already used** (`REPO_ROOT` for 01-04, `PROJECT_ROOT` for 05, `ROOT` for 06) to `DATA_DIR.parent` — so any existing `<root_var> / "data" / ...` expression still resolves to `DATA_DIR / ...`, and `03`/`04`'s `<root_var> / "reports" / "interpretability" / "artifacts"` still resolves to a Volume `reports/` subfolder, without hunting down every downstream reference.

Canonical replacement block (swap in for the root-resolution + sys.path portion only; `<root_var>` is the notebook's own name per the per-variant note below):
```python
DATA_DIR = Path("/Volumes/workspace/default/chec-simulador/data")
<root_var> = DATA_DIR.parent
# --- only for 05 and 06, the two that import the local packages ---
for _p in ("/Workspace/Users/<userName>/databricks-integration/chec_impacto_src",
           "/Workspace/Users/<userName>/databricks-integration/chec_local_interpreter_src",
           "/Workspace/Users/<userName>/databricks-integration/scripts_src"):
    if _p not in sys.path:
        sys.path.insert(0, _p)
```
The `scripts_src` entry is the one that is easy to drop and expensive to debug — see section 3.

**Every staged copy also needs its own dependency install — do not skip this even though the general rule above only touches the root-resolution logic.** The local notebooks assume a pre-configured local Python environment (`pip install -r requirements.txt` run once, outside the notebook); that assumption does not carry over to Databricks, where each notebook run gets a fresh environment. The failure is transitive and therefore unguessable from the notebook's own imports: the archived `09_simulador` failed with `ModuleNotFoundError: No module named 'optuna'` while never mentioning Optuna itself — it imported `chec_impacto.training`, whose `__init__.py` imports `mgcecdl.py`, which does `import optuna` at module level. `05` and `06` import that same package and inherit exactly this risk.

Fix: insert a NEW first cell — literally `nb["cells"].insert(0, ...)`, before the existing markdown title cell — in every one of the 6 staged copies:
```python
%pip install -q -r /Workspace/Users/<userName>/databricks-integration/requirements.txt
```
`%pip install` triggers an automatic Python interpreter restart in Databricks, which is exactly why it must be the very first cell — inserted before, never after, any cell whose state you need to keep. This applies uniformly to all 6, including `01`-`04`, which import no local package but do need `plotly`, `geopandas`, `scikit-learn` and `scipy`.

**A version floor on `plotly` is mandatory for `01`, `03`, `04` and `06`.** All four build their map with `go.Scattermap` and a `{'type': 'map'}` subplot spec — the MapLibre trace family that only exists in modern Plotly. The Databricks Runtime preinstalls an older Plotly, so a bare `plotly` requirement is **already satisfied** and pip upgrades nothing; the failure then surfaces as `ValueError: Unsupported subplot type: 'map'` pointing at the *system* site-packages. `/app-vano-clima`, `/app-trayectorias-circuitos` and `/app-trayectorias-vanos` document the same floor for the same reason — keep them consistent.

**Variant A — `find_repo_root()` over the data file (`01`, `02`, `03`, `04`)**: `<root_var>` = `REPO_ROOT`. All four define the same small helper, which walks up from `Path.cwd()` looking for `data/Indicadores_vano_v3.csv`, and call it as `REPO_ROOT = find_repo_root()`. **None of the four imports `chec_impacto` or `chec_local_interpreter`** — the only mentions of those packages in `02`/`03`/`04` are comments citing where a join rule came from, which is exactly the kind of thing a grep mistakes for an import. So **omit the `sys.path` block entirely** for these four: replace the function definition and its call with the two `DATA_DIR`/`REPO_ROOT` lines and nothing else. Everything else in that cell (`VARS`, `NOMBRES_GRUPOS`, `COLORES_GRUPOS`, `SEMILLA`, the notebook parameters) is untouched and keeps working through the alias.

**Variant B — `resolve_project_root()` over `src/chec_impacto` + `data` (`05`)**: `<root_var>` = `PROJECT_ROOT`. Its bootstrap cell defines `resolve_project_root()` (walks up for a directory holding both `src/chec_impacto/` and `data/`), then `SRC_DIR`, `DATA_DIR`, `DERIVED_DIR`, a `for path_to_add in (PROJECT_ROOT, SRC_DIR)` sys.path loop, and `DERIVED_DIR.mkdir(...)`. Replace the function + its call + that sys.path loop with the canonical block, and **keep `SRC_DIR`, `DERIVED_DIR` and the `mkdir` line** — `DERIVED_DIR` is where its viewer mode looks for the optional OOF `.npz`, and dropping the `mkdir` makes the training path fail on write. Note `DATA_DIR` is defined by both the original cell and the canonical block; let the canonical block's definition win (put it first and delete the original line) rather than leaving two.

**Variant C — `Path.cwd()` walk for `src/` (`06`)**: `<root_var>` = `ROOT`. Replace the `ROOT = Path.cwd().resolve()` walk-up loop and the `for _path_a_agregar in (ROOT, ROOT / 'src')` sys.path block with the canonical block. **Leave the `sys.modules` purge loop and the `_sonda`/`assert hasattr(_sonda, 'caja')` probe that follow them completely untouched** — the purge must still run before the project imports (it is what makes a re-run pick up freshly uploaded package code instead of the copy already cached in the kernel, which is the same failure mode it was added for locally), and the probe is a cheap first-cell contract check.

**`06` writes nothing by default, in Databricks or locally.** The `ipywidgets` app IS its interface everywhere: circuit, window, vano selection, simulator knobs and the "Simular" button all live in the notebook. Running it produces no files and opens no browser, so this command has nothing extra to redirect.

`reports/paneles/06_*.html` behind `EXPORTAR_PANEL_WEB`, carrying a working "Simular" with
